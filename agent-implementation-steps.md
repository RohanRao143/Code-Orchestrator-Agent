# Step-by-Step Multi-Agent Orchestration Implementation Guide

This guide details how to implement a local, memory-safe, hierarchical multi-agent system on your web stack (**Angular, Node.js, Postgres**) and local engine (**Ollama, Python**). 

The architecture is strictly designed to respect a **4GB VRAM hardware limit** (e.g., an RTX 3050) by executing specialized, quantized **3B to 4B parameter models** sequentially, utilizing external state management via Postgres, and actively purging context windows to prevent Out-of-Memory (OOM) crashes.

---

## Architecture Flow Overview

```
 ┌────────────┐       ┌─────────────┐       ┌────────────┐
 │ Angular UI │ ◄───► │ Node.js API │ ◄───► │ PostgreSQL │
 └────────────┘       └──────┬──────┘       └────────────┘
                             │ (IPC / API Call)
                             ▼
                     ┌───────────────┐
                     │ Python Agent  │
                     │ Orchestrator  │ (LangGraph / Ollama)
                     └───────┬───────┘
                             │
            ┌────────────────┼────────────────┬────────────────┐
            ▼                ▼                ▼                ▼
     [Supervisor]      [Architect]        [Coder]         [Reviewer]
  (Decomposes Task)  (Designs Schema)  (Writes Code)    (Syntax Check)
```

## Step 1: Prepare Your Local LLM (Ollama)

To run a memory-safe setup, run only **one small model at a time** in your local Ollama engine. This leaves ample VRAM for context execution.

1. **Pull the base models**:
   Open your terminal and run:
   ```bash
   # Phi-3.5-mini-instruct (3.8B parameters - highly recommended for reasoning and instruction-following)
   ollama pull phi3.5

   # Stable-Code-3B (or deepseek-coder:1.3b/5.7b - optimized for modular code block generation)
   ollama pull stable-code:3b
   ```
2. **Configure Context and Limits**:
   When invoking Ollama programmatically, restrict the context window (`num_ctx`) to **4,096 tokens** to prevent context bloat and OOM issues.

## Step 2: Database Schema (State Store) in Postgres

With 4GB VRAM, keeping everything in the LLM's conversation history will crash your system. You must manage state externally in your **Postgres database**.

Create a tracking schema to store project-wide technical context, task checklists, and active codebase trees.

```sql
-- Track the master project or session state
CREATE TABLE execution_sessions (
    id SERIAL PRIMARY KEY,
    prompt TEXT NOT NULL,
    current_status VARCHAR(50) DEFAULT 'idle', -- e.g., 'analyzing', 'coding', 'reviewing', 'completed'
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Store the checklist of sequential sub-tasks generated by the Supervisor
CREATE TABLE tasks_checklist (
    id SERIAL PRIMARY KEY,
    session_id INT REFERENCES execution_sessions(id) ON DELETE CASCADE,
    step_number INT NOT NULL,
    task_name VARCHAR(255) NOT NULL,
    description TEXT,
    dependencies INT[], -- Arrays of step_numbers that must run first
    status VARCHAR(50) DEFAULT 'pending', -- 'pending', 'in_progress', 'completed', 'failed'
    output_schema TEXT, -- Output structure designed by the Architect
    generated_code TEXT, -- Code produced by the Coder
    review_notes TEXT, -- Feedback from the Reviewer
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Store active project files (external memory representation)
CREATE TABLE project_files (
    id SERIAL PRIMARY KEY,
    session_id INT REFERENCES execution_sessions(id) ON DELETE CASCADE,
    filepath VARCHAR(512) NOT NULL,
    file_content TEXT,
    is_active BOOLEAN DEFAULT TRUE
);
```

## Step 3: Set up the Python Agent Orchestrator

Since **LangGraph** uses a state machine design, it allows you to pause, wipe context memory, and explicitly control transition states. Set up your Python environment (`orchestrator.py`) using LangGraph or a lightweight state equivalent.

```python
import os
import requests
from typing import Dict, List, TypedDict
from langgraph.graph import StateGraph, END

# Define local Ollama client configuration
OLLAMA_API = "http://localhost:11434/api/generate"
DEFAULT_MODEL = "phi3.5"

# State Definition (External to LLM prompt context to keep memory small)
class AgentState(TypedDict):
    session_id: int
    current_step: int
    task_checklist: List[Dict]
    active_code: str
    reviewer_feedback: str
    attempts: int

# Memory-Safe Ollama Caller
def call_local_llm(prompt: str, system_prompt: str = "") -> str:
    payload = {
        "model": DEFAULT_MODEL,
        "prompt": prompt,
        "system": system_prompt,
        "stream": False,
        "options": {
            "num_ctx": 4096,      # Guard context limit strictly
            "temperature": 0.2,   # Lower temperature for coding stability
            "num_predict": 1024   # Clamp predictions to avoid runaway tokens
        }
    }
    response = requests.post(OLLAMA_API, json=payload)
    return response.json().get("response", "")

# 1. Supervisor Agent Node (Decomposes complex requests)
def supervisor_node(state: AgentState) -> Dict:
    # Query Postgres to fetch initial request (done via Node -> Python API)
    session_prompt = "Build a lightweight database connection module in Node.js" 
    
    system_instruction = (
        "You are a Project Supervisor. Break down the user prompt into an ordered JSON array of linear steps. "
        "Do not write code. Just generate the tasks."
    )
    
    response = call_local_llm(session_prompt, system_instruction)
    # Save output to Postgres 'tasks_checklist' here...
    return {"task_checklist": [{"step": 1, "task": "Design database connection schema"}]}

# 2. Architect Agent Node (Designs schemas and contracts)
def architect_node(state: AgentState) -> Dict:
    # "Message Stripping": Only pass target task specifications, not supervisor's logs
    current_task = state["task_checklist"][state["current_step"] - 1]
    
    prompt = f"Design the schema and input parameters for: {current_task['task']}"
    system_instruction = "You are an Architect. Produce only specifications, interfaces, or mock databases in JSON."
    
    response = call_local_llm(prompt, system_instruction)
    return {"active_code": response}

# 3. Coder Agent Node (Generates isolated modular code blocks)
def coder_node(state: AgentState) -> Dict:
    # Pass only the direct Architect specifications and target output, keeping context windows minimal
    architect_output = state["active_code"]
    
    prompt = f"Based on these specs, write the isolated code block:\n{architect_output}"
    system_instruction = "You are a software engineer. Write clean, modular, production-ready code. Output only raw code."
    
    response = call_local_llm(prompt, system_instruction)
    return {"active_code": response, "attempts": state["attempts"] + 1}

# 4. Reviewer/Tester Agent Node (Validates output)
def reviewer_node(state: AgentState) -> Dict:
    code_to_check = state["active_code"]
    
    prompt = f"Analyze this code for syntax correctness:\n{code_to_check}"
    system_instruction = "You are a Reviewer. Return 'PASSED' or point out the specific compilation/syntax bugs."
    
    response = call_local_llm(prompt, system_instruction)
    return {"reviewer_feedback": response}

# Define State Machine Routing Logic
def route_after_review(state: AgentState) -> str:
    if "PASSED" in state["reviewer_feedback"] or state["attempts"] >= 3:
        return "save_and_flush"
    return "coder"  # Loop back to coder if syntax fails

# Compile State Graph
workflow = StateGraph(AgentState)
workflow.add_node("supervisor", supervisor_node)
workflow.add_node("architect", architect_node)
workflow.add_node("coder", coder_node)
workflow.add_node("reviewer", reviewer_node)

workflow.set_entry_point("supervisor")
workflow.add_conditional_edges("reviewer", route_after_review, {"save_and_flush": END, "coder": "coder"})
# (Define other transitions...)
# app = workflow.compile()
```

## Step 4: Implement "Message Stripping" & Context Flushes

To operate safely within **4GB VRAM limits**, configure your execution workflow with these active memory pruning rules:

* **The "Message Stripping" Rule**: When running the Coder Agent, *do not* pass it the raw conversations, reasoning steps, or notes of the Supervisor. Pass only the refined functional spec generated by the Architect and the specific files being modified.
* **Wipe & Flush (`/clear`)**: After a sub-task is completed, verified by the Reviewer, and stored securely on your local workspace disk:
  1. Save the file.
  2. Call the Ollama `/clear` equivalent by releasing LLM memory (killing/refreshing the session payload or running a garbage-collecting call) to reset the context canvas completely.
  3. Load the *next* sub-task step into memory.

## Step 5: Backend Bridge (Node.js API)

Your Node.js app serves as the API orchestrator that initiates agent sessions, updates Postgres, and triggers the Python orchestrator script.

```javascript
const express = require('express');
const { Pool } = require('pg');
const { spawn } = require('child_process');

const app = express();
app.use(express.json());

// Set up Postgres Pool
const pool = new Pool({
  user: 'postgres',
  host: 'localhost',
  database: 'agent_orchestrator',
  password: 'your_password',
  port: 5432,
});

// Endpoint to kick off a multi-agent task sequence
app.post('/api/agents/task', async (req, res) => {
  const { prompt } = req.body;
  
  try {
    // 1. Log the initiation state in Postgres
    const sessionRes = await pool.query(
      'INSERT INTO execution_sessions (prompt, current_status) VALUES ($1, $2) RETURNING id',
      [prompt, 'starting']
    );
    const sessionId = sessionRes.rows[0].id;

    // 2. Spawn the Python Orchestrator process in the background
    const pyProcess = spawn('python3', ['orchestrator.py', sessionId.toString()]);

    pyProcess.stdout.on('data', (data) => {
      console.log(`Orchestrator output: ${data}`);
    });

    pyProcess.on('close', async (code) => {
      console.log(`Agent execution completed with code ${code}`);
      // Update session status in database
      await pool.query('UPDATE execution_sessions SET current_status = $1 WHERE id = $2', ['completed', sessionId]);
    });

    res.status(202).json({ message: 'Agent execution started', sessionId });
  } catch (err) {
    console.error(err);
    res.status(500).json({ error: 'Failed to initiate agent workflow' });
  }
});

app.listen(3000, () => console.log('Node backend running on port 3000'));
```

## Step 6: Frontend Integration (Angular)

In your Angular frontend, build an interface that allows users to prompt the system, track the agent execution status in real-time, and inspect the task checklist.

### Service (`agent.service.ts`)
```typescript
import { Injectable } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { Observable } from 'rxjs';

@Injectable({
  providedIn: 'root'
})
export class AgentService {
  private apiUrl = '/api/agents';

  constructor(private http: HttpClient) {}

  startTask(prompt: string): Observable<any> {
    return this.http.post(`${this.apiUrl}/task`, { prompt });
  }

  // Poll database status or connect via WebSockets
  getTaskStatus(sessionId: number): Observable<any> {
    return this.http.get(`${this.apiUrl}/status/${sessionId}`);
  }
}
```

## Summary of Optimization Tactics for 4GB VRAM
* **Sequential Threading**: Ensure agents never execute in parallel; keep strict task queues [3].
* **State Offloading**: Keep session histories, task queues, and global codebase definitions in Postgres rather than model memory [5].
* **Model Separation**: Keep only a single 3B-4B LLM inside Ollama memory [1, 2].
* **Context Token Capping**: Force `num_ctx = 4096` in agent configs to avoid context scaling crashes [5].
* **Clean Slates**: Flush conversation cache dynamically after every code block passes review [8].
